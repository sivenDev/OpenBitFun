# F002 RFC：跨账号跨设备智能体委派

## 摘要

让本机智能体把任务委派给其他在线 OpenBitFun 设备上开放的智能体，并异步收回结果。目标设备可以属于同一账号，也可以属于另一个账号；目标智能体可以是 OpenBitFun 原生智能体，也可以是该设备上的外部智能体（如 Claude Code）；任务分为纯消息任务和编码任务。

委派复用 F001 的「智能体目录 + 异步委派」抽象：远程智能体出现在智能体列表中，通过 `Task` 后台委派，用 `AgentWait` 取回结果。执行模型复用 Detached Dispatch：任务、会话、事件日志和权限邮箱都由目标端持有，按游标观察，支持幂等提交与能力协商。新增的部分是跨账号信任模型：

- 邀请与配对；
- 按连接授权；
- 连接级端到端密钥；
- relay 的跨账号路由授权；
- 目标端审批与额度。

## 背景与问题

- Detached Dispatch 已经能把任务提交到另一台 OpenBitFun 主机：目标端持有任务、worktree、事件日志与权限邮箱，发起方可以断开，协议有 `probe`、`submit`、`status`、`cancel`、`append`、`continue`、`answer`。但它只交付 Git 工作区，不能指定目标机上的任意目录；relay 不缓存任务；`AskUserQuestion` 不可用。
- 账号设备通道和 Peer Device Mode 都限定为同一账号：relay 在路由前校验账号成员关系，载荷用账号主密钥加密。另一个账号既拿不到这把密钥，也通不过成员校验。
- 智能体目前不能自己发起派发；目标端也没有「对外开放哪些智能体」的概念。
- Dispatch 工作进程以 CLI 交付形态无界面运行，目前没有 ACP 外部智能体的执行能力（见 F001 D8）。
- 参考：OpenBot 的跨账号模式是「主机 + 成员」，用一次性邀请链接或二维码加入，分所有者、管理员、成员三种角色，撤销后结束该成员的所有会话，经 WebRTC 端到端连接。它在条款说明中把「其他人使用你主机上的 Claude」列为高风险用法。

## 目标

1. 目标设备主人可以选择开放哪些智能体，并逐个授权给特定账号或设备；默认不开放、不授权。
2. 跨账号的双方需要先完成邀请与配对，任何一方都可以随时撤销。
3. 发起方的智能体列表中可以看到已授权的远程智能体，标明所属账号、设备、在线状态和兼容性。
4. 助理可以把纯消息任务或编码任务后台委派给远程智能体，不被阻塞；结果回到发起会话。
5. 远程智能体可以是目标设备上的 Claude Code，并使用目标设备自己的登录。
6. 发起方离线或重启后，重新上线时能补收已完成的结果。
7. 目标端的危险操作需要审批，审批人按授权关系确定。
8. 目标离线、版本不兼容、未授权、授权已撤销或超出额度时，委派明确失败并给出原因。

## 非目标

- relay 侧的任务排队，或离线目标的存储转发。
- 任意多跳的互相委派。
- 公开的智能体市场、按陌生人检索智能体。
- 账号之间的计费结算。
- 外部智能体反向委派 OpenBitFun 智能体。

## 决策

### D1 执行复用 Dispatch，信任与路由另建

远程委派就是一次由智能体发起、指定了目标智能体的 Detached Dispatch 任务。执行、幂等、游标观察、取消、追加与审批语义全部沿用 Dispatch。

新增协商能力（暂定名 `agent_delegation_v1`），目标端用它声明支持三件事：按开放智能体执行任务、目录查询、纯消息任务。跨账号另需 `cross_account_delegation_v1`。目标不声明相应能力时，不展示，也不能被委派。版本号相同不能代替能力声明。

### D2 两种关系：同账号与跨账号连接

- **同账号**：沿用现有账号设备通道和账号主密钥，无需配对。
- **跨账号**：引入「连接」这一持久关系。
  - **建立**：一方生成一次性、有过期时间的邀请（链接或二维码），另一方查看邀请内容后接受。
  - **身份**：每台设备有自己的设备身份密钥对，配对时交换并固定对方的公钥，接受邀请前展示指纹供核对。
  - **加密**：跨账号载荷用连接级密钥端到端加密，账号主密钥绝不离开本账号。
  - **撤销**：任一方都能撤销连接，撤销后对方新的委派立即被拒绝，进行中的任务按 D7 处理。

### D3 relay 跨账号路由授权

relay 新增按连接授权的跨账号路由：只有存在有效连接记录的两个设备之间，才能路由委派相关的 RPC。relay 只校验连接与身份，只看到密文，不存储委派内容。

relay 是独立部署的服务，可能与客户端版本不一致：客户端要先确认 relay 声明了跨账号路由能力，才展示跨账号入口；relay 不支持时，入口显示为不可用，并给出原因。

### D4 开放目录与按连接授权

目标端维护开放清单，每个开放项包括：

- 智能体（原生智能体或外部智能体）；
- 展示名与说明；
- 允许的任务类型（纯消息、编码）；
- 纯消息任务使用的工作区（见 D5）；
- 审批策略（见 D7）；
- 额度（见 D8）。

授权是「开放项 × 账号或设备」的组合：同账号设备可以一次授权全部，跨账号必须逐项授权。目录查询只返回请求方被授权的条目。

### D5 两种任务类型

- **编码任务**：沿用 Dispatch 的 Git 交付。以发起方的当前提交为基线，在目标端建立托管 worktree，改动以分支形式带回，不直接写入发起方的工作目录。
- **纯消息任务**：不传输代码。目标智能体在目标主人为该开放项绑定的工作区内运行；未绑定时，在目标端为该连接新建一个独立的空工作区。发起方不能指定目标机上的任何路径。结果是回答文本，外加有大小上限的附件。

### D6 远程外部智能体（Claude Code）

目标端的 Dispatch 工作进程需要具备 F001 D3 下沉后的外部智能体执行能力，并以协商能力（暂定名 `external_agent_executor_v1`）的形式对外声明。

Claude Code 只使用目标设备自己的登录或 API Key，凭据绝不跨设备、跨账号传输。

跨账号授权外部智能体时，目标端在授权界面明确提示：其他账号的请求会消耗目标主人的 Claude 额度，订阅登录用于他人请求可能超出 Anthropic 对订阅「个人日常使用」的限定，并建议改用 API Key。这类授权默认关闭，需要主人显式确认。

### D7 审批、交互与撤销

- 远程委派任务固定使用 Dispatch 的 `remote` 审批策略，权限请求进入目标端权限邮箱。
- **同账号**：审批请求呈现到该账号当前的驱动界面，审批人是账号主人本人。
- **跨账号**：默认由目标主人审批。发起方只能看到「等待对方审批」，不能代替目标主人批准。目标主人可以为某个开放项设置更宽松的策略，比如只读操作自动通过。
- `AskUserQuestion` 沿用 Dispatch 现状：明确失败，不等待。
- 撤销连接或授权时，该连接上进行中的任务被取消；目标端会话保留在目标主人本地，发起方收到「授权已撤销」的结果。

### D8 额度与审计

- **额度**：每个开放项可以设置每个连接的并发任务数和单任务时长上限。这是授权边界上的安全与资源控制，不属于智能体循环内的硬编码限制。
- **审计**：目标端记录每次跨账号委派的来源账号、设备、开放项、任务类型、开始与结束时间和结果状态，主人可以查看。

### D9 发起与结果回收

`Task` 委派给远程智能体时：

1. 发起方按任务类型准备载荷（编码任务先做 Git 基线准备）并提交，立即返回后台任务标识。
2. 发起方持久化一条与发起会话和后台任务关联的出站记录，观察器按游标跟进。
3. 任务结束时，结果作为该后台任务的完成结果交给 `AgentWait`。
4. 发起方重启后，按出站记录重新挂接观察器并补收结果。

### D10 委派链与提示注入

- 委派消息带上来源元数据：账号、设备、会话、智能体。目标端把它展示为「来自某账号某设备的智能体请求」。
- 目标端把委派内容当作不可信输入处理：不提升权限，受开放项的权限上限约束。
- 首期远程委派任务中不暴露远程委派能力，从结构上避免跨设备、跨账号的循环委派；是否开放多跳留给后续 RFC。

### D11 远程场景对照

- **远程控制**：发起方或目标主人用手机端、IM 驱动时，委派、等待、取消、审批都经过内核与权限邮箱。
- **Peer Device Mode**：在对端主机上发起时，出站记录和观察器属于对端主机。
- **远程工作区（SSH）**：编码任务沿用 Dispatch 的 SSH 目标与 Git 交付规则。

## 分阶段交付

每个阶段单独制定开发计划，都需要审批：

1. 同账号，原生智能体，纯消息与编码任务。
2. 同账号，远程外部智能体（Claude Code），依赖 F001 的执行能力下沉。
3. 跨账号：连接与配对、连接级密钥、relay 路由授权、按连接授权、目标端审批、额度与审计。

## 已考虑的替代方案

1. **新建点对点组网与消息邮箱（OpenBot 方案）**：语义灵活，但要重做幂等、恢复、审批与协商，与 Dispatch 重复。执行层未采用；D2 的配对与授权借鉴了它的邀请和角色思路。
2. **跨账号共享账号主密钥，或把对方加为同账号设备**：权限无法收窄，撤销困难，主密钥泄露面扩大。未采用。
3. **由 WebRTC 直连代替 relay**：可以减轻 relay 负载，但要新增 NAT 穿透与新的传输栈，并且与 Dispatch 现有传输重复。首期未采用，以后可以作为新的传输适配器。
4. **纯消息任务允许发起方指定目标路径**：会越过目标主人的目录边界，未采用。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 其他账号经委派对目标机器发起提示注入或越权操作 | 默认不开放、不授权；逐项授权；不可信输入标注；权限上限；目标主人审批；审计；可随时撤销 |
| 连接密钥或身份被冒用 | 设备身份密钥对，配对时核对指纹；连接级密钥；撤销后 relay 立即拒绝路由 |
| relay 与客户端版本不一致 | 先确认 relay 声明了跨账号路由能力；不支持时入口显示不可用 |
| 跨版本目标收到新请求 | 必须声明相应能力；协议只增加可选字段，不改变 Dispatch v6 现有动词语义 |
| 他人请求消耗目标主人的 Claude 订阅（条款风险） | 外部智能体的跨账号授权默认关闭、需要显式确认，建议使用 API Key；凭据不出设备 |
| 资源滥用 | 按连接设置并发和时长额度；审计；撤销 |
| 发起方离线导致结果丢失 | 出站记录持久化，重新上线后补收；结果由目标端任务持有 |
| 纯消息任务在目标机上的数据边界 | 只在主人绑定的工作区或独立空工作区内运行；附件有大小上限 |

## 兼容性、安全与回滚

- **协议**：新增协商能力、目录查询、纯消息任务类型与连接相关请求；Dispatch v6 现有动词语义不变。
- **持久化**：连接、授权、开放清单与审计是新增数据；出站记录新增的关联字段是可选的。读取到无法解析的连接记录时，保留记录、停用该连接并显示原因，不删除。
- **回滚**：撤回能力声明即停止对外开放；关闭 relay 跨账号路由即停止全部跨账号委派；已完成的任务仍可作为普通 Dispatch 任务查看。

## 依赖

- F001：统一子智能体寻址、后台委派生命周期、列表的执行方式字段、外部智能体执行能力下沉（D3）。

## 批准条件（可观察）

1. 目标设备未开放、未授权时，发起方看不到其智能体；同账号开放后可见；跨账号必须先完成配对，并逐项授权后才可见。
2. 同账号下，把纯消息任务和编码任务分别后台委派给远程原生智能体：助理立即继续；纯消息任务返回回答；编码任务把改动以分支形式带回。
3. 把任务委派给远程设备上的 Claude Code：在目标设备上用该设备的登录执行，结果回到发起会话。
4. 跨账号下，目标端的危险操作由目标主人审批，发起方显示「等待对方审批」；撤销连接后，进行中的任务被取消，新的委派被拒绝。
5. 委派运行时关闭再重新打开发起方，结果仍能补收。
6. 目标离线、能力缺失、relay 不支持跨账号、未授权或超出额度时，委派明确失败并给出原因。
7. 远程委派任务内部无法再发起远程委派。
8. 目标端审计记录中可以看到每次跨账号委派。
