# F002 RFC：同账号跨设备智能体委派

## 摘要

让本机智能体把任务委派给同一账号下其他在线 OpenBitFun 设备上、由该设备主人明确开放的智能体，并异步收回结果。委派复用 F001 的「智能体目录 + 异步委派」抽象：远程智能体出现在智能体列表中，通过 `Task` 后台委派、`AgentWait` 取回结果。传输与执行复用 Detached Dispatch：账号设备端到端加密通道、目标端持有的任务、会话、事件日志和权限邮箱，以及能力协商。首期只支持代码任务（Git 工作区交付），不支持跨账号。

## 背景与问题

- Detached Dispatch 已经能把任务提交到另一台 OpenBitFun 主机：目标端持有任务、worktree、事件日志与权限邮箱，发起方可以断开，按游标观察；协议支持 `probe`、`submit`、`status`、`cancel`、`append`、`continue`、`answer`。账号设备通道是端到端加密的，relay 只路由密文，并校验账号成员关系。
- 目前派发由用户在输入框中选择目标后发起，智能体没有可调用的派发入口；目标端也没有「对外开放哪些智能体」的概念。
- Dispatch 只交付 Git 工作区，不能指定目标机上的任意目录；relay 不缓存任务，目标离线时提交直接失败；工作进程以 CLI 交付形态无界面运行，`AskUserQuestion` 不可用。
- Peer Device Mode 与账号设备通道都限定为同一账号。

## 目标

1. 目标设备主人可以选择开放哪些智能体供本账号其他设备委派；默认一个都不开放。
2. 发起方的智能体列表中可以看到在线设备上开放的智能体，并标明设备、在线状态和兼容性。
3. 助理可以把代码任务后台委派给远程智能体，不被阻塞；结果（回答与改动分支）回到发起会话，可通过 `AgentWait` 取回。
4. 发起方离线或重启后，重新上线时能补收已完成的结果。
5. 目标端的危险操作需要审批，审批请求能到达该账号当前的驱动界面。
6. 目标离线、版本不兼容、未开放或能力缺失时明确报错。

## 非目标

- 跨账号（他人电脑）委派、邀请与配对：另行立项。
- 纯消息任务（无 Git 工作区）：首期不支持，在本 RFC 批准后单独评估。
- 远程设备上的外部智能体（如远程的 Claude Code）：依赖 F001 的 D8 后续工作，首期只开放 OpenBitFun 原生智能体。
- relay 侧的任务排队，或离线目标的存储转发。
- 智能体之间任意多跳的互相委派。

## 决策

### D1 复用 Dispatch，而不是新建组网协议

远程委派就是一次由智能体发起的 Detached Dispatch 任务，加上一个指定的目标智能体。传输、加密、幂等、游标观察、取消、追加与审批语义全部沿用 Dispatch。新增一项协商能力（暂定名 `agent_delegation_v1`）：目标端声明支持「按开放智能体执行任务」以及下文的目录查询；不声明该能力的目标不出现在列表中，也不能被委派。版本相同不能代替能力声明。

### D2 目标端开放目录

目标端维护一份由设备主人编辑的开放智能体清单（智能体标识、展示名、说明），持久化在目标端，默认为空。新增只读的目录查询：返回开放清单与目标能力，经账号设备通道调用。发起方按设备缓存查询结果，设备离线时列表显示离线状态，不显示过期条目为可用。

### D3 寻址与列表

远程智能体的寻址由「设备标识 + 智能体标识」组成，作为 F001 统一子智能体类型的一种远程形态。列表项展示设备名、在线状态、兼容性，以及不可用的具体原因。

### D4 发起与结果回收

`Task` 委派给远程智能体时，发起方先执行现有 Dispatch 的工作区准备（以当前提交为基线的托管 worktree），再提交任务，并立即返回后台任务标识。发起方持久化一条与发起会话及后台任务关联的出站记录（沿用 Dispatch 出站记录），观察器按游标跟进；任务结束时，结果作为该后台任务的完成结果交给 `AgentWait`。发起方重启后，根据出站记录重新挂接观察器并补收结果。改动以 Dispatch 现有的分支同步方式带回，不直接写入发起方的工作目录。

### D5 审批与交互

远程委派任务固定使用 Dispatch 的 `remote` 审批策略：目标端的权限请求进入目标端权限邮箱，发起方观察器把它呈现到发起会话和当前驱动界面，回答通过 `answer` 送回。由于是同一账号，审批人就是账号主人本人。`AskUserQuestion` 沿用 Dispatch 现状：明确失败，不等待。

### D6 委派链与防循环

委派消息带上来源元数据（发起设备、发起会话、发起智能体），目标端按「来自另一台设备的智能体请求」展示，并作为不可信输入处理：不提升权限，受目标端权限上限约束。首期在远程委派任务中不暴露远程委派能力。这是一项能力策略，不是按次数的硬编码限制，用来从结构上避免跨设备循环委派；是否放开多跳，留给后续 RFC。

### D7 远程场景对照

- 远程控制：发起方由手机端或 IM 驱动时，委派、等待、取消、审批都经过内核与权限邮箱。
- Peer Device Mode：在对端主机上发起时，出站记录与观察器属于对端主机。
- 远程工作区（SSH）：沿用 Dispatch 现有的 SSH 目标与 Git 交付规则。

## 已考虑的替代方案

1. **新建点对点智能体组网与消息邮箱（OpenBot 方案的跨设备版）**：语义灵活，支持纯消息任务；但要重做加密、幂等、恢复、审批和版本协商，与 Dispatch 大量重复。首期未采用；纯消息任务的评估会把它作为候选。
2. **借用 Peer Device Mode 在对端上直接开会话**：Peer 模式让控制方界面整体切换到对端，不是「本机智能体委派」，而且控制方一断开就无法托管。未采用。
3. **由 relay 排队转发给离线目标**：违反 relay 只路由、不存储的边界，也扩大了密文存储面。未采用。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 被委派的智能体被注入恶意指令（远程提示注入） | 默认不开放；标明来源；按不可信输入处理；受目标端权限上限约束；危险操作需要审批 |
| 跨版本：旧目标收到新请求 | 必须声明 `agent_delegation_v1` 才展示和委派；协议版本不变时只增加可选字段 |
| 发起方离线导致结果丢失 | 出站记录持久化，重新上线后补收；目标端任务持有结果 |
| 工作区交付成本（打包与同步） | 沿用 Dispatch 现有的复用与分块机制；首期只支持 Git 任务 |
| 审批长时间无人回答 | 父会话显示等待审批；沿用 Dispatch 的超时与取消 |
| 目标端凭据与订阅条款 | 目标端只使用自己的模型配置和登录；不跨设备传输凭据（与 Dispatch 规则一致） |

## 兼容性与回滚

- 协议：新增协商能力与目录查询，不改变 Dispatch 协议版本 6 的现有动词语义。
- 持久化：开放清单存于目标端，是新增数据；出站记录新增的关联字段是可选的。
- 回滚：关闭能力声明即停止对外开放；发起方不再展示远程智能体；已完成的任务仍可作为普通 Dispatch 任务查看。

## 依赖

- F001 必须先完成：统一子智能体寻址、后台委派生命周期，以及列表的执行方式字段。

## 批准条件（可观察）

1. 目标设备未开放任何智能体时，发起方列表中看不到它的智能体；开放某个智能体后，发起方能看到它，并标明设备与在线状态。
2. 在发起方助理中把代码任务后台委派给该远程智能体：助理立即继续；任务在目标设备上运行；完成后 `AgentWait` 取回回答，改动以分支形式带回。
3. 委派运行时关闭再重新打开发起方，结果仍能补收。
4. 目标端触发权限请求时，发起方桌面端与手机端都能看到并回答。
5. 目标离线、未声明 `agent_delegation_v1`、或智能体未开放时，委派明确失败并给出原因。
6. 远程委派任务内部无法再发起远程委派。
